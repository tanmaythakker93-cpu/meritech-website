The Meritech approach

Operations built for
the long deployment.

Most IoT operational failures happen well after go-live — a firmware update that silently breaks a subset of the fleet, an anomaly that goes undetected because monitoring thresholds were set at deployment and never revisited, a security incident that escalates because the response runbook was never defined. The original team moves on. The fleet grows. The problems compound.

Meritech IoT Operations Support covers the full post-deployment lifecycle: staged device deployment and commissioning, 24/7 fleet health monitoring with proactive alerting, structured incident management with root cause analysis, continuous security monitoring, periodic maintenance windows, and data analysis that feeds improvement back into the architecture. Your team focuses on the next product. Meritech keeps this one running.

What's included

The full operational
layer for IoT.

Device deployment support
Managing the staged rollout and field commissioning of IoT devices — provisioning, connectivity validation, acceptance testing against defined criteria, and documentation of the deployed fleet baseline. Whether the deployment spans a single site or thousands of endpoints across multiple geographies, each device is validated against the operational specification before being handed over to the monitoring service.
24/7 fleet health monitoring
Continuous round-the-clock monitoring of device uptime, connectivity status, telemetry integrity, battery state, firmware versions, and application-layer health — with configurable alerting thresholds that escalate anomalies to the operations team before they become fleet-wide outages. Monitoring coverage is maintained through a dedicated support portal giving the customer real-time visibility of fleet status at all times.
Incident management & root cause analysis
Structured incident handling from first detection through to root cause documentation and corrective action deployment — with SLA-governed response times, a defined escalation path for severity levels, and post-incident reports that capture what happened, why it happened, and what was changed to prevent recurrence. Root cause analysis is conducted on every significant incident, not just the ones that reach the customer.
Security monitoring & vulnerability management
Ongoing monitoring of the device fleet and cloud platform for security anomalies, unauthorised access attempts, and newly published vulnerabilities affecting the firmware, operating system, or application stack. Security patches and firmware updates are assessed, tested in a staging environment, and deployed to the fleet under a coordinated change management process — minimising the exposure window without disrupting device operation.
Periodic system maintenance
Scheduled maintenance windows covering firmware updates, configuration reviews, certificate renewals, cloud platform health checks, capacity assessments, and connectivity revalidation — carried out to a defined maintenance calendar with pre-agreed change procedures. Periodic maintenance prevents the accumulation of technical debt in a live fleet that makes emergency maintenance windows far more expensive and disruptive.
Data analysis & performance reporting
Regular SLA performance reports, fleet health trend analysis, incident frequency analysis, and operational improvement recommendations delivered on a defined reporting cadence — so the customer always has a documented view of how the deployment is performing against its targets, and a concrete backlog of improvements that can be planned into the product or architecture roadmap.

Questions to ask

Before you hand over
fleet operations.

What does 24/7 monitoring actually cover for an IoT fleet?
Meritech's fleet monitoring covers device connectivity (online/offline status), telemetry integrity (data arriving at the expected rate and within defined value ranges), application health (platform uptime and API response), battery or power state where applicable, firmware version compliance, and security posture. Monitoring thresholds and alert severity levels are defined during the onboarding phase based on the operational requirements of the specific deployment — not applied as generic defaults.
How do you handle incidents for devices in remote or inaccessible locations?
The incident response runbook distinguishes between issues resolvable remotely — OTA firmware updates, configuration pushes, remote reboot, connectivity failover — and those requiring physical access. Remote resolution is always attempted first. Where physical access is unavoidable, the incident report defines the scope of work and estimated resolution timeline before a field visit is dispatched, so the response is coordinated rather than reactive.
What security monitoring is included?
Security monitoring covers anomalous device behaviour, unauthorised access attempts to the cloud platform, certificate expiry tracking, firmware vulnerability scanning, and coordinated patch management. When a CVE is published that affects the firmware or OS on devices in the fleet, Meritech assesses severity, validates the patch in a staging environment, and deploys to the live fleet within the response window defined in the security SLA — not when it's next convenient.
How is this different from a standard IT helpdesk?
A standard IT helpdesk responds to tickets raised by users. Meritech's IoT operations service is proactive rather than reactive — anomalies are detected by the monitoring layer and an incident is raised internally before a user or customer is affected. The operations team understands IoT-specific failure modes: connectivity drop patterns, firmware edge cases, battery degradation, telemetry drift, and OTA rollback — none of which a general helpdesk is equipped to diagnose or resolve.
Can you take over operations for an IoT deployment Meritech didn't build?
Yes. Meritech conducts a transition assessment before taking on operations for an existing deployment — documenting the current architecture, device inventory, connectivity stack, monitoring setup, and known issues. The assessment produces a fleet health baseline and a list of pre-conditions to be resolved before the SLA clock starts. Where the existing deployment has gaps — undocumented devices, expired certificates, missing runbooks — these are addressed during the transition period rather than inherited into the live operations service.
